# الفصل الأول — مقدمة

## 1.1 فكرة المنصة

منصة المُميَّز هي منصة تعليمية إلكترونية متخصصة في تدريس **مادة اللغة العربية** لطلاب **المرحلتين الإعدادية والثانوية في جمهورية مصر العربية**. تقدّم المنصة محتوى تعليميًا منظّمًا يتمحور حول:

- **شرح الدروس** عبر **فيديوهات YouTube** يعرضها المدرّس محمد عفيفي.
- **ملفات PDF** تكميلية (ملخصات، تدريبات، ملاحظات) تُحمى خلف اشتراك مدفوع.
- **مراجعات امتحانية** و**بنوك أسئلة** و**اختبارات تفاعلية**.
- **نظام اشتراكات** يفرّق بين الطالب المشترك وغير المشترك، وحماية المحتوى المدفوع.
- **لوحة تحكّم للمدير** لإدارة الطلاب والدورات والاشتراكات والمدفوعات والإشعارات.
- **ربط ولي الأمر** بالطالب لمتابعة التقدّم.

## 1.2 الهدف من المنصة

الهدف الأساسي هو توفير "مسار تفوّق" منظّم للطالب المصري في اللغة العربية، بعيدًا عن التشتت، من خلال:

1. تجميع المحتوى (فيديو + PDF + تدريب) في مكان واحد.
2. تقييد وصول المحتوى المدفوع خلف نظام اشتراك صارم.
3. إتاحة تجربة مجانية محدودة (Demo / دروس مجانية) لاستقطاب الطلاب.
4. تمكين ولي الأمر من المتابعة والدفع.

## 1.3 الفئة المستهدفة

| الفئة | الوصف | صلاحية الدخول |
|---|---|---|
| طالب (Student) | طالب إعدادي/ثانوي | بريد إلكتروني + مصادقة Firebase أو جلسة |
| ولي الأمر (Parent) | ولي أمر الطالب | دعوة برمز + كلمة سر نصية |
| مدرّس | **غير مُنفَّذ كدور مستقل** — المدرّس "محمد عفيفي" مسجّل كـ `admin` | — |
| مدير (Admin) | صاحب المنصة / المشرف | بريد + كلمة سر نصية |

> **ملاحظة توثيقية:** لا يوجد في الكود دور باسم `teacher` مُنفَّذ. المدرّس يُدار فعليًا بصلاحيات `admin`. هذا قصور وظيفي إن كان المخطط تعدّد المدرسين (انظر الفصل الثالث عشر).

## 1.4 لماذا تم تطويرها

- سد فجوة المحتوى العربي المنظّم رقميًا للثانوية العامة.
- مكننة نموذج أعمال بسيط: اشتراك شهري/سنوي مقابل كشف المحتوى.
- تقليل الاعتماد على ملفات PDF المُ scattered عبر وسائل التواصل.
- إتاحة وصول عبر الويب (PWA) يعمل على الجوال دون تطبيق منفصل مبدئيًا.

# الفصل الثاني — نظرة عامة على النظام

## 2.1 طبيعة البنية الحقيقية (Architecture)

النظام **تطبيق ويب أحادي (Monolith)** مبني بـ **Express 4** يعمل كـ **خادم يقدّم قوالب EJS من جهة الخادم (Server-Side Rendering يدوي)**. لا يوجد فصل بين واجهة عميل (SPA) وخادم REST منفصل بالمعنى الحديث؛ كل المسارات تُعالج في ملف واحد ضخم `app.js` (حوالي 2912 سطرًا).

### سلسلة الإقلاع (Bootstrap Chain)

```
server.js                    (تشغيل محلي: node server.js)
   └─ const app = require('./app')
        └─ app.listen(PORT)          PORT = process.env.PORT || 3000

api/index.js                 (تشغيل Vercel: @vercel/node)
   └─ const app = require('../app')
        └─ module.exports = app       (لا يوجد listen — يستدعيه Vercel كـ handler)
```

أي أن **نفس ملف `app.js`** يُشغَّل محليًا كعمليّة Node طويلة العمر، وعلى Vercel كـ **دالة بدون خادم (Serverless Function)**.

### رسم البنية العامة

```
                         ┌─────────────────────────────────────────┐
                         │            متصفح المستخدم (PWA)         │
                         │  - HTML مُولَّد من EJS (SSR يدوي)       │
                         │  - Service Worker (sw.js / lughati-v4)  │
                         │  - Plyr (CDN) لعرض يوتيوب             │
                         │  - pdf.js (CDN) لعرض PDF               │
                         └───────────────┬─────────────────────────┘
                                         │  HTTPS  (كل المسارات /(.*) )
                                         ▼
                         ┌─────────────────────────────────────────┐
                         │         Vercel Edge / Serverless         │
                         │  vercel.json → api/index.js (@vercel/node)│
                         └───────────────┬─────────────────────────┘
                                         │  require('./app')
                                         ▼
                         ┌─────────────────────────────────────────┐
                         │              Express app (app.js)        │
                         │  - middleware: cookie-session           │
                         │  - middleware: requireAuth/Admin/...   │
                         │  - طبقة التوجيه (Routes)               │
                         │  - data-store.js (ذاكرة + JSON)        │
                         └───────┬───────────────┬───────────┬─────┘
                                 │               │           │
                    ┌────────────▼───┐  ┌────────▼──────┐ ┌─▼──────────────┐
                    │ Firebase Admin │  │ Supabase JS   │ │ YouTube (خارجي) │
                    │ Realtime DB    │  │ Storage (books)│ │ (تضمين embed)   │
                    │ (مخزن موثوق)  │  │ (PDF خاص)    │ │                 │
                    └────────────────┘  └───────────────┘ └─────────────────┘
```

## 2.2 تدفّق البيانات (Data Flow)

### (أ) تدفّق مصادقة الطالب (Firebase)

```
المستخدم → POST /api/auth/firebase-login (idToken)
        → app.js: app.verifyIdToken(idToken)  [firebase-admin]
        → إنشاء req.session.user
        → تعيين كوكي lughati_session (httpOnly, 30 يوم)
        → إعادة توجيه إلى /student
```

### (ب) تدفّق عرض ملف PDF محمي

```
طالب مشترك → GET /student/note-pdf/:noteId
   → requireStudent  ──(إن لم يكن مشتركًا)──▶ subscription-locked
   → app.js: makePdfStream(...)
        → Supabase: createSignedUrl(path, 60s)   [الرابط لا يغادر الخادم]
        → fetch(signedUrl) ──▶ pipe(buffer) ──▶ المتصفح
        → ترويسة: Content-Type, Content-Length, Cache-Control: no-store
   → المتصفح: pdf.js يعرض الصفحات على <canvas>
```

### (ج) تدفّق عرض فيديو الدرس

```
طالب/ضيف → GET /student/lesson/:courseId/:lessonId
   → requireStudentOrGuest (+ فحص اشتراك لبعض الدروس)
   → lesson.ejs: <div data-video="<youtube_embed_url>">
   → main.js: استخراج معرّف يوتيوب + تشغيل Plyr (CDN)
   [لا يوجد أي حماية على رابط يوتيوب نفسه]
```

## 2.3 طبقات النظام (Layers)

| الطبقة | التقنية الفعلية | ملاحظة |
|---|---|---|
| العرض (View) | EJS Templates + CSS يدوي | لا JSX/React |
| التحكّم (Controller) | Express routes داخل `app.js` | Monolith |
| البيانات الوصفية | ملفات JSON في `data/` + Firebase RTDB | RTDB هو الموثوق |
| الملفات الثقيلة | Supabase Storage (حاوية `books`) | PDF فقط |
| الفيديو | YouTube Embeds | خارجي |
| النشر | Vercel (Serverless) | `@vercel/node` |

## 2.4 اقتراحات تحسين البنية

1. **فصل الواجهة عن الخادم** (مثلاً SPA + API) لتقليل حجم `app.js` (2912 سطرًا) الذي يصعب صيانته.
2. **الاعتماد على RTDB أو Supabase DB كمخزن وحيد** بدل ازدواجية JSON + Firebase (انظر الفصل العاشر).
3. **إزالة `react-components/`** المهجور لتجنّب الالتباس.

# الفصل الثالث — التقنيات المستخدمة

> لكل تقنية: تعريف مختصر، سبب الاختيار، المميزات، العيوب، والبدائل. الأقواس تشير إلى وجود فعلي في `package.json`/الكود.

## 3.1 Node.js (بيئة التشغيل)
- **التعريف:** بيئة تشغيل JavaScript مبنية على محرك V8.
- **سبب الاختيار:** تطابق لغة الخادم والعميل (JS)، ونضج النظام البيئي.
- **المميزات:** أداء عالٍ للإدخال/الإخراج غير المتزامن، نظام حزم ضخم.
- **العيوب:** نموذج أحادي الخيط (يحتاج عناية بالعمليات الحجبية).
- **البدائل:** Deno، Bun، Go، Python (FastAPI).

## 3.2 Express.js 4 (إطار الويب) — [موجود]
- **التعريف:** إطار ويب خفيف لـ Node.js.
- **سبب الاختيار:** البساطة، التوافق مع EJS، الانتشار الواسع.
- **المميزات:** middleware chain مرن، توجيه بسيط.
- **العيوب:** لا يفرض بنية (أدّى لملف `app.js` ضخم)؛ انتهاء الدعم الطويل الأمد لـ v4 (يُنصح v5).
- **البدائل:** Fastify، Koa، NestJS.

## 3.3 EJS (محرك القوالب) — [موجود]
- **التعريف:** محرك قوالب من جهة الخادم يولّد HTML.
- **سبب الاختيار:** تكامل مباشر مع Express، بساطة `<% %>`.
- **المميزات:** تضمين أجزاء (partials)، هروب تلقائي `<%= %>`.
- **العيوب:** منطق عرض مختلط أحيانًا؛ لا يدعم SSR حديثًا مثل Next.js.
- **البدائل:** Pug، Handlebars، أو الانتقال إلى React/Next.

## 3.4 JavaScript (Vanilla) — [موجود]
- **التعريف:** لغة البرمجة النصية للعميل والخادم.
- **سبب الاختيار:** لا حاجة لخطوة بناء (build) للواجهة.
- **العيوب:** غياب الأنواع الثابتة (TypeScript) يزيد احتمال الأخطاء.
- **البدائل:** **TypeScript** (موصى به بقوة لتقليل الأخطاء).

> **تنويه:** لا يوجد أي ملف TypeScript مُستخدم في التطبيق. المجلد `react-components/` يحوي `.ts`/`.tsx` لكنه **غير مُستدعى**.

## 3.5 Vercel (الاستضافة) — [موجود]
- يُشرح بالتفصيل في الفصل الرابع.

## 3.6 Firebase Admin SDK + Realtime Database — [موجود]
- **التعريف:** طرف خادم (Admin) للوصول إلى خدمات Firebase دون قيود قواعد العميل.
- **سبب الاختيار:** مصادقة جاهزة للطلاب + مخزن بيانات فوري.
- **المميزات:** مزامنة فورية، استضافة ملفات خدمة (service-account).
- **العيوب:** الاعتماد على مفاتيح خادم حسّاسة؛ حدود Spark (100 اتصال متزامن).
- **البدائل:** Supabase (Postgres)، MongoDB Atlas.

## 3.7 Supabase Storage — [موجود]
- **التعريف:** تخزين كائنات (Objects) عبر `@supabase/supabase-js`.
- **سبب الاختيار:** استضافة ملفات PDF خاصة بروابط موقّعة قصيرة العمر.
- **المميزات:** روابط موقّعة (Signed URLs)، حاويات خاصة.
- **العيوب:** يُستخدم للتخزين فقط (لا DB في هذا المشروع عبر Supabase).
- **البدائل:** Firebase Storage، AWS S3، Cloudflare R2.

## 3.8 YouTube + Plyr — [موجود]
- **التعريف:** استضافة الفيديو على YouTube وتشغيله عبر مشغّل Plyr (من CDN).
- **سبب الاختيار:** تجنّب تكلفة استضافة/بث الفيديو؛ جودة بث يوتيوب.
- **العيوب:** **لا حماية على رابط الفيديو** (أي مستخدم يملك الرابط يشاهده).
- **البدائل:** Vimeo (به حماية مجال)، استضافة ذاتية عبر Mux/BunnyCDN.

# الفصل الرابع — Vercel

## 4.1 نظرة عامة

Vercel هي منصة استضافة تستضيف المشروع على هيئة **دالة بدون خادم (Serverless Function)** عبر البنية `@vercel/node`. ملف `vercel.json` يوجّه كل المسارات `/(.*)` إلى `api/index.js`.

## 4.2 الخطة المجانية (Hobby)

- **السعر:** مجانية تمامًا (لا تتطلب بطاقة).
- **المميزات:** نشر غير محدود للمشاريع (حتى 200 مشروع)، شهادة SSL، CDN عالمي، تحليلات أساسية.
- **الحدود الجوهرية (من وثائق Vercel الرسمية 2026):**
  - 100 عملية نشر/يوم، 100 مشروع.
  - **1 مليون استدعاء دالة/شهر**، **100GB نقل بيانات سريع**، 10GB نقل أصل سريع.
  - 4 CPU-hours، 360 GB-hours ذاكرة مُجهّزة شهريًا.
  - مهلة الدالة: افتراضي 10s، كحد أقصى 60s.
  - سجلات التشغيل لمدة **ساعة واحدة فقط**.
  - حجم قرص 32GB.
- **العيوب:** لا دعم، سجلات قصيرة، مهلة 60s تمنع العمليات الطويلة (مثل رفع ملفات كبيرة عبر الخادم).

## 4.3 الخطة الاحترافية (Pro)

# الفصل الخامس — Supabase

## 5.1 نظرة عامة

في هذا المشروع، **يُستخدم Supabase للتخزين (Storage) فقط**. لا توجد استعانة بـ Supabase Database أو Auth أو Edge Functions ضمن الكود المفحوص. (ملاحظة: الوثائق الرسمية لـ Supabase تشمل هذه المنتجات، وسنذكرها للاطلاع مع توضيح عدم استخدامها هنا.)

## 5.2 Storage (التخزين) — [مُستخدَم فعليًا]

- **الحاوية (Bucket):** `books` — **خاصة** (`public:false`)، تقتصر على `application/pdf`، حد حجم 50MB.
- **الوصول:** **حصريًا عبر روابط موقّعة قصيرة العمر (30–60 ثانية)**؛ لا تُولَّد روابط عامة أبدًا.
- **الدوال (من `supabase-storage.js`):**
  - `isConfigured()` — تتطلب `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`.
  - `ensureBucket()` — تنشئ الحاوية إن لم توجد.
  - `uploadPdf(folder, name, buffer, type)` — رفع المخزن المؤقت.
  - `createSignedUploadUrl(path)` — تتيح رفعًا مباشرًا من المتصفح إلى Supabase (تجاوز حد Vercel).
  - `createSignedUrl(path, expiresIn)` — تُثبّت العمر بين 30–60 ثانية.
- **تدفّق العرض:** يطلب الطالب `/student/note-pdf/:id` → الخادم يُولّد رابطًا موقّعًا 60s، يجلبه (`fetch`) ويُمرّره (pipe) إلى المتصفح **دون أن يصل الرابط للمتصفح**، مع `Cache-Control: no-store`.

## 5.3 Database / Auth / Edge Functions / RLS — [غير مُستخدَمة في هذا المشروع]

| المنتج | هل يُستخدم؟ | ملاحظة |
|---|---|---|
| Supabase Database (Postgres) | لا | البيانات في Firebase RTDB + JSON |
| Supabase Auth | لا | المصادقة عبر Firebase Admin / كلمات نصية |
| Edge Functions | لا | — |
| Row Level Security (RLS) | لا ينطبق | لا توجد جداول Postgres مُدارة هنا |

> للعلم: **RLS** هي طبقة أمان على مستوى الصف في Postgres بـ Supabase تمنع الوصول غير المصرّح به. غير مطبّقة هنا لعدم استخدام DB الخاص بـ Supabase.

## 5.4 الخطط والأسعار (من الوثائق الرسمية 2026)

### الخطة المجانية (Free)
- سعر: 0$. مشروعان مجانيان (يُتوقفان بعد أسبوع من الخمول).
- 500MB قاعدة بيانات، 1GB قرص، 50K مستخدم نشط شهريًا (MAU)، 5GB خروج (egress)، 1GB تخزين، 500K استدعاء Edge Function، 200 اتصال Realtime ذروة.

### الخطة الاحترافية (Pro) — 25$/شهر + حوسبة

- 8GB قرص، 100GB تخزين، 100K MAU، 250GB egress، 2M استدعاء Edge.
- **التجاوزات:** egress 0.09$/GB (غير مخزّن)، 0.03$/GB (مخزّن)؛ التخزين 0.0213$/GB؛ قرص DB 0.125$/GB؛ MAU 0.00325$ لكل مستخدم بعد 100K.

### الخطة المؤسسية (Enterprise)

## 5.5 كيف تستفيد منصة المُميَّز من Supabase؟

# الفصل السادس — Firebase

## 6.1 نظرة عامة

يُستخدم Firebase في هذا المشروع عبر **`firebase-admin` (طرف الخادم)** للوصول إلى **Realtime Database**، وللمصادقة عبر التحقق من **`idToken`** المُرسل من العميل. لا يوجد استخدام موسّع لقواعد حماية العميل (لأن الوصول من الخادم يتجاوزها).

## 6.2 Authentication

- الطلاب: يسجّلون عبر Firebase Auth (الواجهة)، ثم يُرسلون `idToken` إلى `POST /api/auth/firebase-login`؛ يُتحقق منه خادميًا بـ `fbAuth.verifyIdToken`.
- المدير/ولي الأمر: **كلمات سر نصية** في `users.json` (غير مُجزّأة — خطر أمني، انظر الفصل السابع).
- **Firebase Auth مجاني** لمعظم الطرق (بريد/كلمة).

## 6.3 Realtime Database (RTDB)

- **الدور:** المخزن الموثوق للبيانات (يُنسخ إليه من JSON عند البذر).
- `firebase-admin.js` يقرأ/يكتب RTDB ويعكس إلى JSON محلي كاحتياط.
- `scripts/seed-firebase.js` (عبر `npm run seed`) يبذر RTDB من ملفات `data/`.
- **الحدود (Spark):** 1GB مخزّن، 10GB مُنزَّل/شهر، **100 اتصال متزامن**.
- **تجاوز الحد (Blaze):** 5$/GB مخزّن، 1$/GB مُنزَّل.
- 200,000 اتصال متزامن لكل قاعدة على Blaze (تعدّد القواعد للتوسّع).

## 6.4 Security Rules

- طرف الخادم (Admin) **يتجاوز** قواعد الحماية؛ لذا الأمان يعتمد على منطق `app.js` (middleware).
- لا توجد قواعد RTDB مُدارة من جهة العميل في هذا السياق (لأن الكتابة تتم عبر Admin).

## 6.5 الخطط: Spark مقابل Blaze

| وجه المقارنة | Spark (مجاني) | Blaze (مدفوع) |
|---|---|---|
| بطاقة دفع | غير مطلوبة | مطلوبة |
| تخزين RTDB | 1GB | نفس المجاني + 5$/GB زائد |
| تنزيل/شهر | 10GB | + 1$/GB زائد |
| اتصالات متزامنة | 100 | 200,000/قاعدة |
| تجاوز الحد | قطع صارم | فوترة زائدة |
| Cloud Storage | يتطلب Blaze (من 2026-02-03) | متاح |

## 6.6 أفضل الممارسات

1. **تقييد قواعد RTDB** حتى لو كان الوصول عبر Admin (دفاع متعدد الطبقات).
2. **عدم كشف `service-account.json`** (موجود في شجرة العمل كاحتياط — خطر).
3. **الانتقال إلى Supabase Postgres** لاستعلامات أقوى إن نمت البيانات.
4. **مراقبة الاتصالات المتزامنة** لتفادي حظر Spark.

# الفصل السابع — الأمان

## 7.1 Authentication (المصادقة)

- **الآلية:** `cookie-session` بكوكي اسمه `lughati_session`، `httpOnly:true`, `sameSite:'lax'`, `secure` في الإنتاج، `maxAge: 30 يومًا`.
- **السر الافتراضي:** `process.env.SESSION_SECRET || 'lughati-secret-key-2026'` — **سر ضعيف مُثبّت افتراضيًا** (خطر تزوير جلسة إن لم يُضبط المتغير).
- **المصادقة:** الطلاب عبر Firebase `idToken`؛ المدير/ولي الأمر عبر **مقارنة نصية** (`password === password`) — **لا تشفير**.

## 7.2 Authorization (الترخيص)

دوال middleware مُسمّاة صراحةً في `app.js`:

| الدالة | الشرط |
|---|---|
| `requireAuth` | وجود `req.session.user` |
| `requireAdmin` | `role === 'admin'` |
| `requireStudent` | `student`/`admin` |
| `requireStudentOrGuest` | طالب/مدير/ضيف/وضع تجريبي |
| `requireParent` | `role === 'parent'` |
| `checkSubscription` | اشتراك فعّال وإلا يُعلَّم منتهيًا + إشعار FCM |
| `refreshSession` | مزامنة حقول الجلسة من DB (كل 30s) |

## 7.3 حماية ملفات PDF

- الأقوى في النظام: حاوية Supabase خاصة + رابط موقّع ≤60s **يُمرَّر عبر الخادم** (لا يصل للمتصفح).
- **الملاحظات (Notes):** تطلب اشتراكًا فعليًا وإلا `subscription-locked`.
- **قصور:** واجهة العرض (`pdf-viewer.ejs`) تعطّل النقر/الحفظ/الضغط على F12 — **تخبيب واجهة فقط (UX obfuscation)**، يمكن تجاوزه بسهولة؛ الصفحات تُرسم على `<canvas>` ويمكن التقاطها.

## 7.4 Signed URLs

- تُستخدم في Supabase (`createSignedUrl`, `createSignedUploadUrl`) بعمر 30–60 ثانية.
- **ممتازة لمنع إعادة استخدام الرابط**، لكنها لا تمنع مشتركًا شرعيًا من الالتقاط داخل النافذة الزمنية.

## 7.5 JWT

- لا يوجد استخدام صريح لـ JWT مخصص؛ رمز Firebase `idToken` هو أساسًا JWT تُتحقق منه عبر `verifyIdToken`.

## 7.6 حماية الفيديوهات

- **غير محمية.** الفيديوهات يوتيوب مضمّنة (embed) بلا قفل مجال (domain lock) أو رابط موقّع. أي حامل للرابط يشاهد المحتوى.
- الحماية تقتصر على **مستوى صفحة الدرس** (دخول + اشتراك)، لا على الفيديو نفسه.

## 7.7 حماية قواعد البيانات

- RTDB يُصل إليه عبر Admin (تجاوز القواعد).
- لا توجد قواعد حماية مُدارة من جهة العميل ضمن الكود.

## 7.8 إدارة الجلسات

- إنشاء: `req.session.user = sessionUser(user)` (حقول خفيفة لتقليل حجم الكوكي).
- تدمير: `POST /logout` يضبط `req.session = null`.
- تحديث دوري عبر `refreshSession` (خنق 30s).

## 7.9 الصلاحيات حسب الدور

| الدور | الصلاحيات | المخاطر |
|---|---|---|
| طالب (Student) | عرض الدروس/PDF المسموح + الاختبارات + الملف الشخصي | لا يملك إلا بياناته |
| ولي الأمر (Parent) | متابعة تقدّم الابن | كلمة سر نصية |
| مدرّس (Teacher) | **غير مُنفَّذ** | — |
| مدير (Admin) | تحكّم كامل (طلاب/دورات/اشتراكات/مدفوعات/إشعارات/رفع PDF) | كلمة سر نصية `admin123` في البذور |

## 7.10 ملخص الثغرات الأمنية (موثّق من الكود)

| الثغرة | الشدة | الدليل |
|---|---|---|
| كلمات سر نصية | عالية | `app.js` مقارنة مباشرة؛ `users.json` |
| لا تشفير (bcrypt/argon2) | عالية | غير موجود |
| لا حماية CSRF | متوسطة | كل المسارات POST بلا رمز |
| لا حدّ للسرعة (Rate Limiting) | متوسطة | تسجيل/OTP مفتوح |
| لا Helmet/ترويسات أمان | متوسطة | لا CSP/X-Frame-Options/HSTS |
| سر جلسة افتراضي ضعيف | عالية | `'lughati-secret-key-2026'` |
| `service-account.json` في شجرة العمل | عالية | ملف مفاتيح فعلي |
| فيديوهات بلا حماية | متوسطة | يوتيوب embed |
| حماية PDF قابلة للالتفاف | منخفضة | تخبيب واجهة فقط |

- Supabase Storage يوفّر Edge/CDN للملفات.

## 8.5 تحسين المكوّنات (Next.js / React)

- **لا ينطبق** — المشروع EJS/Vanilla. (لو وُجد Next.js لكانت التوصية: `next/image`، `dynamic import`، ISR.)

## 8.6 تحسين Firebase

- تقليل أحجام القراءة من RTDB؛ الاعتماد على المرآة المحلية (`data-store.js`) لتقليل استدعاءات الشبكة.

- استخدام الروابط الموقّعة بدل تنزيل الخادم للملف بالكامل عند الإمكان.

## 8.8 توصيات عملية

1. تفعيل **Helmet** لترويسات أمان وأداء.

# الفصل العاشر — النُسخ الاحتياطي (Backup & Recovery)

## 10.1 Backup

- **RTDB:** تصدير تلقائي/يدوي عبر Firebase (يُنصح بجدولة تصدير يومي إلى Cloud Storage).
- **Supabase Storage:** نسخ الحاوية `books` دوريًا (لم يُنفَّذ تلقائيًا في الكود).

## 10.2 Recovery

- الاستعادة من RTDB export.
- إعادة البذر عبر `npm run seed` عند فقدان البيانات المحلية.

## 10.3 Disaster Recovery

- **خطة موصى بها:** تصدير RTDB يومي ← Cloud Storage ← نسخ إلى حساب آخر. نسخ حاوية Supabase أسبوعيًا.
- **النقص الحالي:** لا توجد أتمتة نسخ في الكود؛ الاعتماد الكلي على RTDB دون نسخة ثانية.
